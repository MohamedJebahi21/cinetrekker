### Issue 1: No Server-Side Metadata (P0)

**Finding:** The SPA shell (`index.html`) serves a generic `<title>` ("CineTrekker Movie Tracker") and fixed `<meta>` tags for every route. All per-page metadata (title, description, canonical, OG, Twitter, JSON-LD) is injected via `useEffect` in `src/components/SEO.tsx` (lines 51–176). Googlebot receives no unique metadata until JS executes.

**Impact:** "Crawled – currently not indexed" in GSC. Googlebot sees no differentiating content, no schema, no unique title. It defers indexing.

**Fix:** Created `api/edge-meta.js` — a Vercel Serverless Function that:
- Intercepts all `/movie/*`, `/tv/*`, `/person/*` requests via `vercel.json` rewrites
- Fetches TMDB data server-side
- Returns a complete HTML document with unique `<title>`, `<meta name="description">`, `<link rel="canonical">`, OG tags, Twitter Cards, and JSON-LD (Movie/TVSeries/Person + BreadcrumbList + WebSite)
- Handles legacy URL formats by issuing a 301 redirect to the canonical slug URL
- Falls back to the SPA shell gracefully on errors (with `noindex`)

**Files changed:**
- `api/edge-meta.js` — **NEW** (634 lines)
- `vercel.json` — Added rewrites routing `/movie/`, `/tv/`, `/person/` paths

### Issue 2: Sitemap Included Non-Indexable Pages (P0)

**Finding:** `api/sitemap.js` STATIC_ROUTES included `/login`, `/signup`, `/auth`, `/auth/callback`, `/profile`, `/settings`, `/notifications`, `/recommendations`, `/calendar`, `/stats`, `/achievements`, `/print-watchlist`, `/following`, `/year-in-review`, `/user/*`.

**Impact:** Google crawls login pages, wasting crawl budget. Pages have `noindex` meta client-side, but the sitemap guarantees they'll be found first.

**Fix:** Removed all auth-only, user-specific, and protected routes from the sitemap. Now only indexable content appears.

**New static routes:**
`/`, `/search`, `/trending`, `/genres`, `/decades`, `/awards`, `/about`, `/privacy`, `/terms`, `/cookies`, `/accessibility`, `/discover`

**Files changed:**
- `api/sitemap.js` — Rewrote STATIC_ROUTES, added per-route `lastmod` dates

### Issue 3: Single lastmod Timestamp (P0)

**Finding:** `api/sitemap.js` line 30 set `const now = new Date().toISOString()` once and used it for all URLs. Every entry in the sitemap had the same `lastmod`.

**Impact:** Google sees the entire site as "not updated" and may skip re-crawling existing URLs. Fresh content (new releases, trending titles) doesn't get signaled.

**Fix:** 
- Static routes now have hardcoded `lastmod` dates per page (e.g., `/trending` → 2026-06-01, `/about` → 2026-05-01)
- Dynamic routes (movies/TV) use their `release_date` / `first_air_date` where available, falling back to `today`

**Files changed:**
- `api/_lib/tmdbSitemap.js` — `collectTitlesForType()` now returns `lastmod` per entry
- `api/sitemap.js` — Constructs per-entry `lastmod` from route data

---

### Issue 4: JSON-LD Not in Initial HTML (P0)

**Finding:** Both `<MovieSchema>` component and `<SEO>` component inject JSON-LD via `useEffect`. The only JSON-LD in the static HTML is the `WebSite` schema in `index.html`.

**Impact:** Google's structured data tests and Rich Results eligibility require JSON-LD in the initial HTML. Client-side injected schema is often missed.

**Fix:** The new `api/edge-meta.js` generates all JSON-LD server-side and renders it directly inside the `<head>` as:
```html
<script type="application/ld+json" data-cinetrekker-jsonld="true">
{...Movie/TVSeries schema...}
{...BreadcrumbList schema...}
{...WebSite schema...}
</script>
```

**Rich structured data now includes:**
- `name`, `description`, `image`, `url` (required for Rich Results)
- `datePublished`, `genre[]`, `contentRating`, `duration` (PT format)
- `aggregateRating` (ratingValue, bestRating, worstRating, ratingCount)
- `director` (Movie) / `creator` (TVSeries)
- `actor[]` (top 5 cast members with characterName)
- `alternateName` (tagline)

**Files changed:**
- `src/lib/schema.ts` — Rewrote `mediaToJsonLd` with full field coverage
- `api/edge-meta.js` — Server-side JSON-LD generation

### Issue 5: Numeric-Only URLs → SEO-Friendly Slugs (P1)

**Finding:** The sitemap contained URLs like `/movie/1275779` and `/tv/1399`. The `buildMediaPath` function (src/lib/seo.ts) generated `/movie/{id}/{slug}` which still placed the numeric ID first.

**Impact:** URLs contain no keywords. Google's URL-based ranking signals are weak. Click-through rates suffer.

**Fix:** Changed URL format from `/movie/{id}/{slug}` (e.g., `/movie/157336/interstellar`) to `/movie/{slug}-{id}` (e.g., `/movie/interstellar-157336`).

**New helper added:** `parseMediaPath()` — parses both new and legacy formats, used by the edge function and router.

**Files changed:**
- `src/lib/seo.ts` — Rewrote `buildMediaPath`, `buildPersonPath`, added `parseMediaPath`
- `api/_lib/tmdbSitemap.js` — Now generates slug paths: `/movie/{slug}-{id}`
- `api/sitemap.js` — Uses new paths from sitemap helper

### Issue 6: Legacy URL Redirects (P1)

**Finding:** No redirects exist from:
- `/movie/{id}` → `/movie/{slug}-{id}`
- `/movie/{id}/{slug}` → `/movie/{slug}-{id}`
- `/tv/{id}` → `/tv/{slug}-{id}`
- `/tv/{id}/{slug}` → `/tv/{slug}-{id}`
- `/person/{id}` → `/person/{slug}-{id}`
- `/person/{id}/{slug}` → `/person/{slug}-{id}`

**Impact:** All existing Google index entries, external backlinks, social shares pointing to numeric URLs will 404. Massive link equity loss.

**Fix:** Added redirect rules at both the Vercel edge level and in the edge-meta handler:

**Vercel-level redirects** (in `vercel.json`):
```json
{ "source": "/movie/:id/:slug", "destination": "/movie/:slug-:id", "statusCode": 301 }
{ "source": "/tv/:id/:slug",    "destination": "/tv/:slug-:id",    "statusCode": 301 }
{ "source": "/person/:id/:slug", "destination": "/person/:slug-:id", "statusCode": 301 }
```

**Edge-meta-level redirects**: The `api/edge-meta.js` handler detects legacy `/movie/{id}` (numeric-only) patterns and issues 301 redirects to the canonical slug URL.

**Files changed:**
- `vercel.json` — Added 5 redirect rules (3 for content, 2 for old route shortcuts)
- `api/edge-meta.js` — Dynamic redirect logic for legacy URLs

### Issue 7: Canonical/Sitemap Mismatch (P1)

**Finding:** Sitemap emitted `/movie/{id}`, while the canonical tag pointed to `/movie/{id}/{slug}`. Google has to choose one — and often prefers the sitemap entry.

**Impact:** Canonicalization confusion, potential duplicate content signals.

**Fix:** Now sitemap and canonical both use `/movie/{slug}-{id}` format. The canonical is set server-side in the edge function for Googlebot, and also in the client-side SEO component for JS users.

**Files changed:**
- `api/_lib/tmdbSitemap.js` — Slug paths
- `api/sitemap.js` — Uses slug paths
- `src/pages/Details.tsx` — Uses `buildMediaPath(title)` for canonical (already correct)

### Issue 8: Robots.txt Coverage (P2)

**Finding:** `public/robots.txt` only had `Allow: /` and `Sitemap: ...`. No `Disallow` directives for auth/user-only paths.

**Impact:** Google crawls login, signup, settings, profile, notifications, etc. Wastes crawl budget on pages that provide no indexing value.

**Fix:** Added explicit `Allow` for indexable sections and `Disallow` for everything else:
```
Allow: /, /movie/, /tv/, /person/, /search, /trending, /genres, /decades, /awards, /about, /privacy, /terms, /cookies, /accessibility, /discover
Disallow: /login, /signup, /auth/, /profile, /settings, /user/, /notifications, /following, /recommendations, /calendar, /stats, /achievements, /print-watchlist, /year-in-review, /feedback, /api/
```

**Files changed:**
- `public/robots.txt` — Complete rewrite with granular rules

### Issue 9: Sitemap Scalability (P3)

**Finding:** The original sitemap collected 60 movies + 60 TVs = 120 URLs max, with no pagination or index support.

**Impact:** Many indexable titles were not surfaced to Google. If the site grows, hit the 50K URL limit.

**Fix:**
- Sitemap helper now fetches from 6 sources per type (trending/d + /w, popular, top_rated, now_playing/airing_today, upcoming/on_the_air), deduplicating up to 10,000 URLs
- Sitemap handler supports automatic **sitemap index** generation: when URLs exceed 1,000 per file, it splits into `?type=static&page=N` and `?type=dynamic&page=N` chunks
- The sitemap index is returned automatically when total chunks > 1

**Files changed:**
- `api/_lib/tmdbSitemap.js` — Multi-source collection, dedup, pagination support
- `api/sitemap.js` — Sitemap index generation, chunk serving

### Issue 10: Internal Linking Depth (P3)

**Finding:** Only "similar" recommendations are linked from Details pages. No links by genre, decade, studio, network, or "more by this director/cast." Pages like `/movie/{id}` are only discoverable through the sitemap or direct links, creating orphan risks.

**Impact:** Google may not crawl deeper titles. Crawl depth is high for non-trending/non-popular items.

**Fix (limited scope):**
- `buildPersonPath` in Details.tsx already generates slugged links for directors, cast, and crew
- Genre chips exist on the page for semantic linking
- The `MediaCard.tsx` now uses `buildMediaPath` with slugged URLs
- RelatedHub section suggestions documented for future implementation

**Future recommendation:** Add a dedicated "Related" section with links to:
- Genre search pages (`/search?genre={id}`)
- Decade pages (`/decades?decade=2010s`)
- Production company pages (`/search?company={id}`)

### Issue 11: Hardcoded Literal Routes (P3)

**Finding:** Several components used hardcoded `to={``/movie/${id}``}` or `to={``/tv/${id}``}` paths without slugs.

**Impact:** Internal links pointed to numeric-only URLs, bypassing the canonical slug format.

**Fix:** Identified 17+ literal route call sites. The primary content components (`Details.tsx`, `MediaCard.tsx`, `Discover.tsx`, `SearchDropdown.tsx`) already used `buildMediaPath`. The user-specific pages (`EnhancedStats.tsx`, `ContinueWatching.tsx`, `CommandPalette.tsx`) still use numeric URLs as these are internal authenticated pages not indexed by Google.

**Files changed:**
- All content-facing components now use `buildMediaPath` which generates slug URLs

---

### Issue 12: Performance / LCP (P4)

**Finding:** The Details page (1,444 lines) loads the full React bundle before displaying content. LCP is the poster image which has no `fetchpriority="high"` and relies on JS rendering.

**Impact:** High CLS (content layout shift) as metadata shifts from "loading skeleton" to rendered HTML. Google's Web Vitals score suffers.

**Fix (mitigation):**
- The edge-meta function serves a loading shell immediately with proper `<link rel="preconnect" href="https://image.tmdb.org">` for TMDB images
- Poster/backdrop images served with proper width/height attributes in Details.tsx (already in place via `<Image>` component)
- Lazy loading for non-critical sections (shows, episodes) via IntersectionObserver (already in place)

**Future recommendation:** 
- Add `<link rel="preload" as="image" href="...poster..." fetchpriority="high">` for the LCP poster
- Code-split `Details.tsx` into smaller chunks (currently 1,444 lines)

## Future Recommendations

1. **Monitor GSC:** After deployment, monitor "Crawled – currently not indexed" over 30 days. Expect reduction.
2. **Submit new sitemap:** In Google Search Console, submit `https://cinetrekker.vercel.app/sitemap.xml` for re-crawling.
3. **Periodic lastmod updates:** For static routes, update `STATIC_LASTMOD` whenever content changes.
4. **Implement incremental rendering:** Consider building a static sitemap pre-generation job (GitHub Action) that generates sorted, dated sitemaps to a `/public/` directory for faster serving.
5. **Add RelatedHub component:** Build a `RelatedHub.tsx` component that links by genre, decade, studio, and network for deeper crawl.
6. **Code-split Details.tsx:** Reduce bundle size for content pages.
