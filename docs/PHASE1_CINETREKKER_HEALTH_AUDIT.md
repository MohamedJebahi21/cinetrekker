# CineTrekker Phase 1 Health Audit

**Scope.** This audit reviewed the current production site at `https://cinetrekker.vercel.app` as an unauthenticated first-time visitor, inspected the full local codebase and Supabase migrations, ran the repository’s targeted security and unit tests, and exercised desktop and 390×844 mobile routes. No application code, database policy, Vercel configuration, OAuth setting, or remote service was changed during this phase.

> **Overall assessment:** CineTrekker has a strong technical baseline: direct content routes work, primary discovery/search/detail flows work, guest actions are optimistic, security headers are robust, and the local Lighthouse result is excellent. The launch blockers are concentrated rather than widespread: one visible production localization defect, unprotected upstream proxy capacity, a distributed-rate-limit availability/security inconsistency, and a first-run journey that feels like a dense title catalog before it feels like a personal tracker.

## What was verified

| Area | Result | Evidence |
|---|---|---|
| Direct movie, TV, and person routes | **Working** | Representative direct paths returned HTTP 200; movie detail rendered metadata and trailer player. |
| Search and no-results recovery | **Working** | A zero-result query rendered a query-specific empty state with Home and Trending recovery links. |
| Trending and discovery | **Working in this session** | Movie and TV grids loaded successfully; prior outage was not reproduced. |
| Guest tracking | **Working** | Adding a title immediately changed the action to Remove and showed an “Added to Watchlist (guest)” acknowledgement. |
| Guest watchlist | **Working, with one copy defect** | The saved item persisted into Watchlist; the page clarified device-local persistence. |
| Protected profile route | **Working** | `/profile` redirected to sign-in with an explanatory message. |
| Mobile basic layout | **Working** | Home, Search, Trending, Watchlist, and Login had no document-level horizontal overflow at 390×844. |
| Security regression tests | **Passing** | Four API-security scenarios passed, including auth mismatch, invalid-token throttling, cron bypass, and feedback abuse. |
| Continue-watching unit tests | **Passing** | Eight episode-progress scenarios passed. |
| Browser console | **No errors observed** | No console output across sampled unauthenticated live journeys. |
| Lighthouse, local production preview | **Strong, with bundle opportunity** | Performance 99, Accessibility 100, Best Practices 96, SEO 100; Lighthouse estimates 242 KiB unused JavaScript. |

## 1. Bugs

| Priority | What and where | Why it matters | Effort | Verification for the fix |
|---|---|---|:---:|---|
| **P1** | **Raw i18n key is visible on live Watchlist.** The third guest queue stat renders `stats.totalHours` instead of a label. `src/components/WatchlistStats.tsx` calls `t("stats.totalHours") || "Hours"`, but the English catalog does not define that key. | This is an immediately visible quality failure on a core first-run path. It also demonstrates that the current i18n check can pass while source keys are missing. | S | Add the English key, supply catalog translations, render Watchlist in every supported language, and make the CI audit fail when source keys are absent. |
| **P1** | **The public TMDB proxy has no shared request-security/rate-limit middleware.** `api/tmdb-proxy.js` accepts permitted arbitrary TMDB paths and query values, but unlike feedback, social, and recommendation endpoints it does not invoke `enforceRequestSecurity`. | An unauthenticated visitor can use CineTrekker as a bounded upstream proxy and consume the project’s TMDB quota. It raises availability and cost risk even though the API key is not exposed. | M | Add origin validation and distributed rate limiting; confirm legitimate detail/search/discovery flows work and repeated proxy calls receive 429 with a user-safe recovery state. |
| **P1** | **TMDB proxy response bodies expose upstream diagnostic details.** `api/tmdb-proxy.js` returns `errorText` and caught exception messages in JSON `details`. | Upstream and infrastructure diagnostics need not be public. The same endpoint should give visitors a stable, friendly error while logging provider detail privately. | S | Induce an upstream failure in a test; confirm the client receives only a safe error code/message and server logs retain diagnostic context. |
| **P2** | **Guest tracking feedback is inconsistent across routes.** Grid cards toast “Added to Watchlist (guest)” but do not explain it is device-local; Watchlist does explain this. | A new user can reasonably believe their first action is already cross-device. That is a trust and conversion problem rather than a persistence failure. | S | Add concise, consistent guest-state language on the toast/action surface and confirm it does not appear for signed-in users. |
| **P2** | **Authenticated Profile, follow, rating, and real persistence flows could not be exercised end-to-end in this read-only audit.** The code and targeted tests were reviewed, but no test account was created. | The highest-value stateful user flows still need a controlled authenticated regression pass before declaring launch-ready. | M | Use a dedicated test account; verify immediate optimistic UI, refresh persistence, cross-tab behavior, unauthorized mutation rejection, and profile privacy. |

## 2. Code Issues

| Priority | What and where | Why it matters | Effort | Verification for the fix |
|---|---|---|:---:|---|
| **P1** | **Distributed rate limiting silently falls back to per-instance memory when Redis is absent or fails.** `api/_lib/requestSecurity.js` does this for missing credentials, non-OK Redis responses, and network exceptions. | This defeats globally consistent throttling during an outage or misconfiguration. It is especially risky for the unauthenticated, high-cost recommendation endpoint. It also conflicts with the desired production security posture. | M | Decide and document the production policy; recommended default is fail closed for expensive/mutating endpoints with a clear 503, while retaining narrowly scoped in-memory fallback only for non-sensitive local development. Test both Redis-success and Redis-failure paths. |
| **P1** | **The i18n audit checks locale parity but not source-key existence.** `npm run i18n:verify` passed even though the live source uses a key absent from English. | CI currently certifies a broken translation path. The error pattern `t(key) || fallback` is also unsafe because i18next commonly returns the key string, which is truthy. | M | Extend `scripts/check-i18n-keys.mjs` to extract source keys and compare them with English; replace unsafe fallback patterns with i18next default-value usage or a typed translation helper. |
| **P2** | **Profile is an oversized page-level component.** `src/pages/Profile.tsx` contains a very large amount of orchestration, rendering, analytics, form, and social logic. | Large components increase regression probability, make review difficult, and are already complicating the separate profile improvement work. | L | Extract profile hero, tabs, activity, favorites, statistics, edit settings, and data selectors; preserve existing behavior with targeted tests around each module. |
| **P2** | **Supabase typing has escape hatches in profile/social surfaces.** `src/services/profile.ts`, `src/pages/UserProfile.tsx`, and `src/pages/People.tsx` use explicit `any` or broad `unknown as` casts. | Schema/RPC changes can compile while producing malformed runtime reads or writes. This is especially sensitive around public-profile privacy and social data. | M | Regenerate or maintain typed database definitions, type RPC return shapes, and add tests for malformed/missing records. |
| **P2** | **Search intentionally suppresses a mixed-response typing problem.** `src/pages/Search.tsx` contains `@ts-expect-error` for a combined multi-endpoint response. | The compiler warning is not documenting a stable contract; it masks one. A TMDB response variation can become a customer-visible search regression. | M | Introduce an explicit discriminated union/normalizer for discover results and unit-test movies, TV, people, and mixed payloads. |
| **P3** | **Live root HTML is `no-store`.** This protects freshness and was not measured as a live performance failure, but it may reduce repeat-navigation efficiency if the policy is applied more broadly than needed. | The app already serves assets with an efficient cache policy, so the risk is limited. It deserves route-level cache review, not a blanket change. | S | Profile real repeat-visit navigation and ensure only HTML/edge metadata remains non-cacheable while immutable assets keep long-lived cache headers. |

## 3. UX Gaps

| Priority | What and where | Why it matters | Effort | Comparator and direction |
|---|---|---|:---:|---|
| **P1** | **The first action does not visibly create a personal story.** Home and Trending foreground a very large title catalog plus repeated Watchlist/Watched controls. The “Weekly Spotlight” copy is polished but does not quickly show what one saved or watched title will unlock. | CineTrekker can feel like a generic TMDB browser before it feels like a personal tracker worth returning to. | M | Letterboxd explicitly teaches one small watched action, then explains how it becomes Films, Diary, profile taste, activity, and year-end recall. Make CineTrekker’s first save/watched action show the next personal payoff. [1] [2] |
| **P1** | **Guest-to-account conversion is context-poor.** Watchlist correctly explains device-local data, but generic card toasts and the Sign Up page do not carry through the visitor’s actual saved title or sync benefit. | The highest-intent moment—the moment after a visitor tracks something—is not used to make the account value concrete. | S | Preserve the immediate action in the signup message: “Keep *The Odyssey* and future progress across devices.” Trakt’s public promise connects tracking and sharing before the join CTA. [3] |
| **P1** | **Repeated per-card controls create visual and focus overload.** The 390×844 Trending audit found 227 focusable elements, predominantly repeated Watchlist and Watched buttons. | Mobile remains layout-safe, but scanning and keyboard/touch navigation are burdensome. The visual hierarchy favors controls over the titles users are trying to evaluate. | M | Keep the primary action visible; move the secondary state into a compact overflow/quick-action pattern and offer an accessible direct “mark watched” route. IMDb uses persistent view preferences; action density should match the chosen browsing mode. [4] |
| **P2** | **Current discovery lacks a visible return loop.** Home has discovery rails but no strong “continue current show,” “episodes released since your last visit,” “friends watched,” or “your week in screen time” story for a returning user. | A tracker earns habit through timely personal state, not only through fresh global content. | L | TV Time, Serializd, and Simkl all foreground episode progression, reminders/new releases, diary/history, and personal or social activity. Introduce one focused return module before adding more global rails. [5] [6] [7] |
| **P2** | **The account/profile journey is not fully narrated for a new user.** The app has a public-profile/social code surface and profile settings, but the unauthenticated journey does not make public taste, lists, or activity feel like a reward for tracking. | Users may create an account only to see another catalog rather than a record of themselves. | M | Serializd makes profile personality, favorite shows, sharing, diary, and stats part of its public proposition; Letterboxd presents the profile as an evolving reflection of taste. [1] [6] |
| **P2** | **Analytics and advanced destinations arrive before the core habit is clear.** Menu/discover routes expose many destinations, while the entry journey has no compact onboarding sequence or explicit next step after an action. | Feature breadth can read as static or template-like instead of intentional. | M | Add a lightweight first-three-actions path: save a title, mark something watched, then see a generated “your taste is taking shape” state. Use progressive disclosure rather than more navigation. |
| **P3** | **Loading and data-failure recovery could be more visibly branded.** The audited happy paths were responsive and no console errors were observed, but upstream-detail errors currently surface raw diagnostics through the proxy and the empty/error strategy is not standardized across all async modules. | Consistent loading, retry, and human-language error states are part of a premium tracker feel. | M | Standardize skeleton, compact inline-retry, and empty-state patterns. Keep motion under 300 ms and use it to confirm state changes, not decorate every row. |

## Recommended Phase 2 sequence

The next work should be delivered in reviewable batches. **Batch A: security and correctness** should fix the raw i18n key and strengthen the TMDB proxy plus production rate-limit policy. **Batch B: test coverage and data contracts** should make source-key i18n validation mandatory, normalize Search results, and add the authenticated regression matrix using a dedicated test account. **Batch C: first-run experience** should reduce card action density, make guest sync limitations consistent, and add a contextual post-action conversion surface. **Batch D: returning-user engagement** should add one personal continuation/recap module and only then expand diary, social, lists, or profile depth.

## Audit limitations and decisions needed

The audit did not create an account, submit a feedback form, modify any cloud configuration, or run a live database/RLS introspection. Those actions require explicit authorization or dedicated test credentials. The current source includes social-profile migrations that have not been confirmed as applied to the remote database; therefore real public-profile, follow, and comment interaction behavior remains **unverified**, not assumed broken.

Before Phase 2, confirm the desired production behavior when the distributed rate-limit provider is unavailable. The recommended security posture is to fail closed for high-cost and mutating endpoints (recommendations, feedback, social mutations), return a clear temporary-unavailable message, and reserve a local in-memory fallback for development only.
